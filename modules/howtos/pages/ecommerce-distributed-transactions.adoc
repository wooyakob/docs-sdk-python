This guide walks through a practical e-commerce scenario — a fashion retailer — to demonstrate how to use Couchbase distributed ACID transactions from the Python SDK.
Every business-critical operation (placing an order, fulfilling it, processing a return, or running a flash sale) is wrapped in a single atomic transaction that spans multiple documents.

Refer to xref:howtos:distributed-acid-transactions-from-the-sdk.adoc[] for a comprehensive reference on the transactions API.

== Overview

A modern fashion retailer stores its data across several document types:

[cols="1,2,3"]
|===
| Document key pattern | Type | Purpose

| `product::{sku}` | `product` | Catalog entry — name, brand, price, description
| `inventory::{sku}::{size}::{color}` | `inventory` | Per-variant stock levels
| `customer::{id}` | `customer` | Customer profile, loyalty points, order history
| `order::{uuid}` | `order` | Order created atomically by a transaction
|===

Without distributed transactions, updating several of these documents requires complex application-level compensation logic.
With Couchbase transactions, all documents are updated atomically — either all changes commit together, or none of them do.

== Error Handling

Couchbase transactions surface two distinct exception types that require different handling strategies.

`TransactionFailed`::
The transaction *definitely did not commit*.
No changes were applied to any document.
The application can safely retry or surface the error to the user.

`TransactionCommitAmbiguous`::
The transaction *may or may not have committed*.
This can happen when a network or node failure occurs after the transaction reached the commit point but before the client received confirmation.
The application should query the affected documents to determine the actual state before deciding to retry.

== Rollback on Business Logic Errors

Raising any exception inside the transaction {lambda} triggers an automatic rollback.
This makes it straightforward to enforce business rules atomically:

[source,python]
----
# Inside the transaction lambda
if inv["quantity_available"] < quantity:
    raise ValueError("Out of stock")  # rolls back all changes made so far
----

The SDK will not retry the transaction after a user-raised exception — it propagates the exception to the caller wrapped in `TransactionFailed`.

== Concurrency Considerations

The Couchbase transactions protocol handles document-level locking automatically.
If two concurrent transactions attempt to modify the same inventory document, one will detect the conflict and retry transparently.

However, you should *never* mix transactional and non-transactional writes to the same document within the same request path.
Non-transactional writes (e.g. `collection.replace()`) can silently overwrite a transaction's staged mutations.

See xref:concept-docs:transactions.adoc#concurrency-with-non-transactional-writes[Concurrency with Non-Transactional Writes] for details.

== Configuration Reference

The transaction configuration used in this example:

[source,python]
----
TransactionConfig(
    durability=ServerDurability(DurabilityLevel.MAJORITY),  # <1>
    expiration_time=timedelta(seconds=30),                  # <2>
)
----

<1> `MAJORITY` durability requires the write to be persisted on a majority of replicas before the transaction commits.
This is the recommended setting for production e-commerce workloads.
<2> `expiration_time` sets the maximum wall-clock time a transaction may run.
Long-running transactions hold document locks longer, so keep this value as low as your workload allows.
